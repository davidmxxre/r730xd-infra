## 1. Objective and scope

At the end of this module the host has:

- a second RAID5 array (`hdd`) on the three Seagate disks, carrying volume
  group `hdd-vg` with three mounted filesystems (backups, bulk, ISOs);
- an offline package repository on `hdd-vg` so software can be installed
  with no network;
- a thin pool (`vmpool`) in `ssd-vg` ready to hold VM disks, with space held
  back for snapshots of the root volume;
- the KVM/libvirt stack installed, hardware acceleration confirmed, and
  `virsh` talking to the system hypervisor;
- local monitoring: SMART checks on all six disks, RAID event alerts, a
  raised SCSI timeout on the desktop-class disks, and a weekly array scrub.

It also records the SSD, boot and root layout that the installer created,
because nothing else in the repository describes it.

**Out of scope:** the OS install (done 2026-10-23); any networking beyond
the iDRAC cable (Module 0.5); DNS, identity, central logging, metrics,
backups (Phase 1); turning NTP back on (Module 1.1); buying a UPS (ADR-0007);
creating any VM.

**Network posture:** the host is not on the home LAN and stays off it until
Module 0.5 or an explicit need. Access is the iDRAC direct cable and its
serial console.

## 3. Design decisions

Each decision gives the options, the criteria, the choice, what would change
it, and where you will meet the same decision again.

### D1. How do we protect RAID5 against the write hole? (ADR-0011)

**Background:** see concept 4.4. A RAID5 array that loses power mid-write
can be left with data and parity that disagree. If a disk then fails, the
rebuild uses the wrong parity and silently returns corrupt data.

| Option | Closes the hole | Cost | Needs |
|---|---|---|---|
| Write-intent bitmap | No. It only shortens the resync after a crash | Small write overhead | Nothing |
| Partial Parity Log (PPL) | Yes | Slower writes; a full resync is no longer needed after a crash | RAID5, v1.x metadata |
| Journal device | Yes | A dedicated fast disk, which becomes a single point of failure unless mirrored | A spare device |
| UPS with clean shutdown | Removes the trigger (power loss), not the hole | Money | ADR-0007 |

**Criteria:** does the host lose power uncleanly; is there a spare device;
how much write performance matters on that tier.

**Decision:** PPL on the new `hdd` array. There is no UPS, no spare device,
and the HDD tier holds backups, where correctness matters more than write
speed. Bitmap and PPL cannot be enabled together, so choosing PPL means
giving up the bitmap.

**Still open:** `pv00` (the SSD array under root and every VM) was created
by the installer with a bitmap and no PPL. It is exposed to the write hole
today. Either convert it (procedure in the runbook, section "Convert pv00 to
PPL") or close ADR-0007 with a UPS. Do one before VMs hold data that
matters.

**What would flip it:** a UPS that shuts the host down cleanly makes the
bitmap acceptable again and gets back the write speed.

**Where you meet this again:** any parity RAID without a battery-backed
controller cache. Hardware RAID cards solve it with that battery; software
RAID has to solve it some other way.

### D2. RAID level for the HDD tier (ADR-0012)

| Option | Usable | Survives | Rebuild behaviour |
|---|---|---|---|
| RAID5, 3 disks | about 1.8 TiB | 1 disk | reads both survivors end to end |
| RAID1, 3-way mirror | about 0.9 TiB | 2 disks | copies one disk |
| RAID10 | needs 4 disks | — | — |

**Decision:** RAID5. The tier holds backups, ISOs, the package repository
and later packet captures; capacity matters and everything on it is a copy
of something else or can be re-created.

**The weak point you accept:** these are desktop disks. A rebuild reads
every sector of the two survivors, which is exactly when a hidden bad sector
shows up. D3 and the weekly scrub exist to find those sectors early.

**What would flip it:** if this tier ever holds the only copy of something,
or if a fourth disk is added (then RAID10 or RAID6).

### D3. Desktop disks in an array: the timeout problem (ADR-0013)

**Background:** see concept 4.9. A desktop disk that hits a bad sector may
retry internally for a minute or two. The kernel waits a fixed time for any
command (90 seconds with this controller driver), then resets the disk. The
RAID layer sees an I/O error and ejects a disk that was only slow.

| Option | Effect |
|---|---|
| Leave the default | A recoverable bad sector can cost you a disk, and during a rebuild that means the array |
| Tell the disk to give up quickly (error-recovery control) | The right fix, but these disks do not support it |
| Raise the kernel's timeout above the disk's worst case | The disk gets time to finish; the array stalls for up to that long but stays whole |
| Buy NAS/enterprise disks | Solves it properly; costs money |

**Decision:** raise the timeout to 180 seconds on the three Seagate disks
with a udev rule, and scrub the array weekly so bad sectors are found while
there is still redundancy to repair them from.

**Limit:** the kernel timeout is the part we control. The controller
firmware has its own patience and can still drop a stalled disk.

**What would flip it:** replacing the disks with ones that support
error-recovery control; then set a short disk-side limit instead.

**Where you meet this again:** every time someone builds an array from
cheap disks. `smartctl -l scterc` tells you which kind you have.

### D4. Where do VM disks live, and what does libvirt manage? (ADR-0014)

| Option | Snapshots | Complexity | Problem |
|---|---|---|---|
| qcow2 files on a filesystem | qcow2 internal | low | stacks a second thin layer on top of LVM; charter rules it out |
| libvirt "logical" pool on `ssd-vg` | none usable | low | that pool type only creates ordinary (thick) volumes |
| Thin LVs created by hand, attached as raw block devices | LVM thin snapshots | you run `lvcreate` yourself | none for this project |

**Decision:** one thin pool, `vmpool`, taking 90% of the free space in
`ssd-vg`. Each VM disk is a thin LV in that pool, handed to the VM as a raw
block device. libvirt manages one pool only, a directory pool for ISO
images on `hdd-vg`.

Three choices inside that:

- **Root stays thick.** If the thin pool fills, every thin volume in it
  stalls. Root is not in the pool, so the host itself keeps running.
- **About 180 GiB stays unallocated in `ssd-vg`.** A snapshot of a thick
  volume needs its own space outside the pool. This is the space for
  "snapshot root before a risky change".
- **512K chunk size, zeroing left on.** Larger chunks mean less metadata
  and better throughput, at the cost of coarser snapshots. Zeroing new
  chunks is slower but stops one VM reading another's deleted data.

**Known limit:** TRIM does not pass through this controller to the SSDs
(section 5.1 shows the evidence). Space freed inside a VM returns to the
pool only if the VM issues discards, and never reaches the SSD firmware.

**What would flip it:** a second host (then shared storage), or a need for
file-level portability of VM disks (then qcow2).

### D5. Where does the offline package repository live? (ADR-0015)

| Option | Problem |
|---|---|
| Mount the USB stick whenever needed | A headless host then depends on a stick being plugged in |
| Copy to the root filesystem | 12 GB of a 50 GiB root that should stay small and easy to snapshot |
| Copy to `hdd-vg/bulk` | `dnf` now depends on `/srv/bulk` being mounted |

**Decision:** `hdd-vg/bulk`, at `/srv/bulk/repo/rhel9.5`. Bulk read-only
data belongs on the bulk tier. The dependency on the mount is recorded in
the runbook.

**What would flip it:** connecting the host to a network with a real
mirror or a Red Hat subscription (Module 0.5 onward).

## 4. Concepts

### 4.1 The storage stack on this host

Every layer presents a block device to the layer above it. Learn to read
`lsblk` output as this picture.

```
 physical disk        /dev/sdX   (name changes between boots)
      |                /dev/disk/by-id/ata-<MODEL>_<SERIAL>   (stable)
 partition            sda1, sda2, sda3      (HDDs here are used whole)
      |
 md RAID array        /dev/md/hdd   -> /dev/md124
      |               combines several disks into one device with redundancy
 LVM physical volume  the array, labelled for LVM's use
      |
 LVM volume group     hdd-vg        a pool of space made from PVs
      |
 LVM logical volume   /dev/hdd-vg/bulk  =  /dev/mapper/hdd--vg-bulk
      |               a slice of the group; this is what you format
 filesystem           xfs           turns blocks into files and directories
      |
 mount point          /srv/bulk     where the filesystem appears in the tree
```

Each layer has its own tool and its own way of reporting health. When
something is wrong, work down the stack: is it mounted (`findmnt`), does the
volume exist (`lvs`), is the group there (`vgs`), is the array up
(`/proc/mdstat`), are the disks present (`lsblk`), are the disks healthy
(`smartctl`).

### 4.2 Device names: why `/dev/sdX` cannot be trusted

The kernel hands out `sda`, `sdb`, ... in the order it discovers disks.
Plug in a USB stick, change a cable, or reboot, and the letters can move.
On this host the Seagate disks were `sdb`, `sdd`, `sde` during the build;
they may not be next boot.

udev (concept 4.10) creates stable names as symbolic links:

| Path | Based on | Use it for |
|---|---|---|
| `/dev/disk/by-id/ata-ST1000DM010-2EP102_W9A63479` | model and serial number | anything that targets one physical disk |
| `/dev/disk/by-id/wwn-0x5000c500...` | World Wide Name burned into the disk | same, when you do not have the serial |
| `/dev/disk/by-uuid/<UUID>` | the filesystem's own ID | `/etc/fstab` |
| `/dev/md/hdd` | the name stored in the array | the array |
| `/dev/hdd-vg/bulk` | LVM names | volumes |

Rule for this project: a command that could destroy data never takes an
`sdX` name typed from memory.

### 4.3 RAID 1 and RAID 5

RAID combines disks so that losing one does not lose data.

- **RAID1 (mirror):** every disk holds the same data. Two disks, one disk's
  capacity. Any member can be read on its own, which is why the boot
  partitions use it.
- **RAID5 (striping with parity):** data is cut into **chunks** (512 KiB
  here). A **stripe** is one chunk per disk. In each stripe, all disks but
  one hold data and the last holds **parity**, the XOR of the data chunks.
  The parity position rotates from stripe to stripe.

```
            disk A     disk B     disk C
 stripe 0   data 0     data 1     PARITY
 stripe 1   data 2     PARITY     data 3
 stripe 2   PARITY     data 4     data 5
```

  With three 1 TB disks you get two disks of capacity. If a disk dies, each
  missing chunk is recomputed from the other two.

Words you will see in `mdadm` output:

| Term | Meaning |
|---|---|
| clean / active | all members present, parity believed correct |
| degraded | one member missing; still works, no redundancy left |
| recovering / rebuild | a new member is being filled in from the others |
| resync | parity is being recalculated across the whole array |
| check (scrub) | read everything and compare data with parity |
| spare | a member that is attached but not yet in use |

**Small writes cost more on RAID5.** Changing one chunk means reading the
old data and old parity, computing new parity, and writing both. This is
the read-modify-write penalty and it is why RAID5 is slower for random
writes.

**A rebuild is the dangerous moment.** It reads every sector of the
surviving disks. Any unreadable sector found then has no second copy to
repair it from.

### 4.4 The write hole, the bitmap, and PPL

Updating a stripe means writing a data chunk and the parity chunk. They are
two separate writes to two disks. If power is lost between them, the stripe
holds new data with old parity (or the reverse). Nothing notices, because
the array is not degraded and reads do not use parity. Later a disk fails,
that stripe is rebuilt from parity that does not match, and you get wrong
data with no error. That is the **write hole**.

- A **write-intent bitmap** records which regions were being written. After
  a crash the array resyncs only those regions. It makes recovery fast. It
  does not make it correct if a disk is also missing.
- **PPL (Partial Parity Log)** writes a small record of the parity
  information before each partial-stripe write, in the metadata area of the
  member disks. After a crash that record is enough to make the stripe
  consistent. It closes the hole and costs write speed.
- The two use the same space, so an array has one or the other.

`mdadm --detail` shows which is active on the line `Consistency Policy`.

### 4.5 md superblocks, metadata versions and array names

Each member of an array carries a **superblock**: a small record saying
which array it belongs to (UUID), the array's name, the RAID level, and
this member's role. `mdadm --examine` reads it.

- **Metadata 1.2** puts the superblock near the start of the member. This
  is the default.
- **Metadata 1.0** puts it at the end. The EFI partition uses 1.0 so that
  the firmware, which knows nothing about RAID, sees an ordinary FAT
  filesystem starting at the beginning of the partition.

The array's **name** is stored as `host:name`, for example
`r730xd-01:hdd`. When the stored host matches the running host, udev makes
the link `/dev/md/hdd`. The kernel's number (`md124`) is only the order of
assembly and can change. `/etc/mdadm.conf` holds `ARRAY` lines that pin a
name to a UUID.

### 4.6 LVM: physical volumes, volume groups, logical volumes

LVM sits between arrays and filesystems so that volumes can be created,
resized and snapshotted without repartitioning.

- **PV (physical volume):** a block device handed to LVM. Here, an array.
- **VG (volume group):** a pool of space made of one or more PVs, divided
  into **extents** (4 MiB each by default).
- **LV (logical volume):** a set of extents presented as a block device.

An LV has two equivalent paths: `/dev/hdd-vg/bulk` and
`/dev/mapper/hdd--vg-bulk`. In the second form a hyphen inside a name is
doubled, because a single hyphen separates the VG from the LV.

LVM sizes are binary: `-L 300G` means 300 GiB.

### 4.7 Thick volumes, thin pools and snapshots

A **thick** LV owns all its extents from the moment it is created. A 50 GiB
thick LV uses 50 GiB whether or not anything is written.

A **thin pool** is an LV that other LVs draw from on demand. A **thin LV**
has a virtual size (`-V 40G`) and consumes real space only as data is
written. The pool is two hidden volumes: `_tdata` (the blocks) and `_tmeta`
(the map of which thin LV owns which block).

```
 ssd-vg
 ├── root        50 GiB   thick
 ├── swap         8 GiB   thick
 ├── vmpool      1.6 TiB  thin pool  (vmpool_tdata + vmpool_tmeta)
 │    ├── vm-a   40 GiB virtual, uses what it has written
 │    └── vm-b   ...
 └── (free)     ~180 GiB  kept for snapshots of root
```

Two things follow from "on demand":

- **Over-provisioning.** The virtual sizes can add up to more than the
  pool. That is useful and it is a risk: when the pool's data or metadata
  reaches 100%, writes to every thin LV in it stall. Watch `Data%` and
  `Meta%` in `lvs`.
- **Cheap snapshots.** A snapshot of a thin LV is another thin LV sharing
  the same blocks. It is created instantly and uses space only as the two
  diverge. This is the "snapshot before, roll back after" mechanism the
  security range depends on.

A snapshot of a **thick** LV works differently: it needs its own reserved
space in the VG, given with `-L`. That is why 180 GiB is left free.

### 4.8 Filesystems, UUIDs, `/etc/fstab` and mount topology

`mkfs.xfs` writes an empty XFS filesystem onto a block device and gives it a
random **UUID**. **Mounting** attaches that filesystem at a directory.

`/etc/fstab` lists what to mount at boot. Six fields per line:

```
UUID=723273be-...  /srv/bulk  xfs  defaults  0  0
     what            where    type  options  dump  fsck-order
```

Which filesystem a path belongs to is decided by the nearest mount point
above it. `/srv` is a plain directory on root. `/srv/bulk` is a mount
point. So `/srv/bulk/repo` is on `hdd-vg` only while `/srv/bulk` is
mounted. If you create and fill that directory before mounting, the files
land on root and are hidden the moment the mount happens.

### 4.9 SCSI command timeouts and error-recovery control

The kernel gives every disk command a deadline, readable and writable at
`/sys/block/<disk>/device/timeout`. On this controller driver the default
is 90 seconds. When it expires the kernel aborts the command and resets
the device.

Disks sold for arrays support **error-recovery control** (ERC, also sold as
TLER): they stop retrying a bad sector after a few seconds and report the
error, so the array can rebuild that sector from parity and carry on.
Desktop disks retry for as long as they like. If that is longer than the
kernel's deadline, the kernel resets a disk that was still working on it.

### 4.10 `/proc`, `/sys` and udev

`/proc` and `/sys` are not on disk. They are views into the running kernel
presented as files. Reading a file asks the kernel a question; writing to
one changes a setting, for the current boot only.

- `cat /proc/mdstat` asks the md driver for array status.
- `echo check | sudo tee /sys/block/md124/md/sync_action` tells it to start
  a scrub.

**udev** is the service that reacts when the kernel announces a device. It
runs through rule files in `/usr/lib/udev/rules.d/` and
`/etc/udev/rules.d/`, and those rules create the `/dev/disk/by-*` links,
set permissions, and can write `/sys` settings. Because a `/sys` setting is
lost at reboot, anything you want applied to a device every time it appears
goes in a udev rule.

### 4.11 SMART

Every disk keeps health counters and can test itself. **SMART** is the
interface to that. `smartctl` asks once; `smartd` asks on a schedule and
raises an alert when something changes. The counters that predict failure:

| ID | Name | Meaning when it rises |
|---|---|---|
| 5 | Reallocated_Sector_Ct | sectors replaced from the spare area |
| 197 | Current_Pending_Sector | sectors the disk could not read and has not yet replaced |
| 198 | Offline_Uncorrectable | sectors that failed during a self-test |
| 199 | CRC_Error_Count | corruption on the cable or backplane, not the platters |
| 177 | Wear_Leveling_Count (Samsung) | SSD wear; the normalized value counts down from 100 |

### 4.12 KVM, QEMU and libvirt

Three layers, often spoken of as one:

- **KVM** is a kernel module (`kvm_intel` here) that lets a process run
  guest code directly on the CPU using Intel VT-x. It appears as
  `/dev/kvm`.
- **QEMU** is the program that is the virtual machine: one process per VM,
  emulating its disks, network cards and firmware, using KVM for the CPU.
  Without KVM it still works by pure emulation, many times slower.
- **libvirt** is the management service. It stores each VM's definition as
  XML, starts and stops QEMU, and manages storage pools and virtual
  networks. `virsh` is its command line.

libvirt has two separate worlds on one machine:

| URI | Runs as | Use |
|---|---|---|
| `qemu:///system` | root | the host's real VMs; this project always uses it |
| `qemu:///session` | your own user | private, unprivileged; what `virsh` picks if you are not root and have not said otherwise |

Objects defined in one are invisible in the other.

On RHEL 9 libvirt runs as a set of small **modular daemons**, one per job
(`virtqemud`, `virtstoraged`, `virtnetworkd`, ...), started on demand by
systemd sockets. The older single daemon, `libvirtd`, still ships but is
deprecated, and the two must not run together.

### 4.13 Package repositories and `dnf`

A **repository** is a directory of RPM packages plus an index in
`repodata/`. `dnf` reads `.repo` files in `/etc/yum.repos.d/` to learn
where repositories are (`baseurl`), whether they are on (`enabled`) and
which key to check signatures against (`gpgkey`). RHEL splits its content
into **BaseOS** (the core system) and **AppStream** (everything else,
including the virtualization stack). The install DVD carries both, so a
copy of those two directories is a complete offline repository.

A **package group** is a named set of packages. An **environment group** is
a set of groups; "Virtualization Host" is one.

### 4.14 Secure Boot

With Secure Boot on, the firmware runs only a signed bootloader, which runs
only a signed kernel, which loads only signed kernel modules. Everything
Red Hat ships is signed. A module you build yourself is not, and will be
refused unless you enrol your own key with `mokutil`. Nothing in this
module is affected; it matters the day a third-party driver is needed.

### 4.15 Privilege and the shell: why `sudo echo x > file` fails

`sudo` runs one program as root. The shell that reads your command line is
still running as you, and it is the shell, not the program, that opens the
file named after `>`. So in `sudo echo check > /sys/...` the redirect is
attempted as dave and refused before `sudo` even starts.

The fix is to make a root program do the writing:

```
echo check | sudo tee /sys/block/md124/md/sync_action
```

`echo` runs as you and writes to the pipe. `tee` runs as root, reads the
pipe, and writes the file. Add `-a` to append instead of overwrite, and
`>/dev/null` if you do not want `tee`'s copy on the screen.

The second trap: `sudo -i` starts a new root login shell. Variables you set
as dave do not exist there.
