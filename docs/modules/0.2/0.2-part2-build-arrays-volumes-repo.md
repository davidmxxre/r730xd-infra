# Module 0.2 — Part 2 of 4: build procedure, sections 5.0 to 5.4

Verify the host, build the HDD array, put LVM and filesystems on it, build
the offline repository.

## 5.0 Conventions

- You are logged in as `dave`. Commands that need root start with `sudo`.
- Writing to a root-owned file uses `| sudo tee FILE` (concept 4.15).
- Disks are named by `/dev/disk/by-id/...`, arrays by `/dev/md/<name>`,
  volumes by `/dev/<vg>/<lv>`. `sdX` names appear only in sample output.
- Every command block follows the same order: purpose, command, breakdown,
  what it changes, expected output, failure cases, verify, undo, why this
  way.
- Sample output is from this host on 2026-11-09.

## 5.1 Verify the as-built state

### Tool card: `lspci`

| | |
|---|---|
| What it is | Lists devices on the PCI bus and, on request, the kernel driver bound to each. Package `pciutils`. |
| Reads from | `/sys/bus/pci` for the devices, `/usr/share/hwdata/pci.ids` for the names |
| Use it when | You need to know what hardware is present and which driver runs it: after a hardware change, when a NIC or controller is not behaving, before PCI passthrough |
| Related | `lsusb` (USB), `lsblk` (disks), `lscpu` (CPU), `dmidecode` (firmware tables), `lsmod` (loaded modules) |
| Grammar | `lspci [display options] [selection options]` |
| Safety | Read-only |
| Help | `man 8 lspci` |

| Option | Meaning |
|---|---|
| `-k` | add "Kernel driver in use" and "Kernel modules" lines |
| `-nn` | show names and the numeric IDs in brackets |
| `-n` | numeric IDs only |
| `-v`, `-vv` | more detail; run with `sudo` to see everything |
| `-s 02:00.0` | only the device at that address (bus:device.function) |
| `-d VENDOR:DEVICE:CLASS` | only matching IDs; any field may be left empty |
| `-t` | tree showing which bridge each device hangs off |

### Command 1 — confirm the controller and its driver

Purpose: everything below assumes disks are passed through raw by the H330
on the `megaraid_sas` driver.

```
lspci -nnk -d ::0104
```

| Token | Meaning |
|---|---|
| `lspci` | the tool |
| `-nn` | print names plus numeric IDs |
| `-k` | print the driver lines (`-nn` and `-k` are combined as `-nnk`) |
| `-d ::0104` | vendor empty, device empty, class `0104`, which is "RAID bus controller" |

Changes: read-only.

Expected:

```
02:00.0 RAID bus controller [0104]: Broadcom / LSI MegaRAID SAS-3 3008 [Fury] [1000:005f] (rev 02)
	DeviceName: Integrated RAID
	Subsystem: Dell PERC H330 Mini [1028:1f4b]
	Kernel driver in use: megaraid_sas
	Kernel modules: megaraid_sas
```

How to read it: `02:00.0` is the PCI address. `[0104]` is the class.
`[1000:005f]` is chip vendor and device. `Subsystem` is the card as Dell
sells it. `Kernel driver in use` is what is running it now; `Kernel
modules` is what could.

If it fails: no output means no device of that class. Run `lspci -nnk` and
look for the controller; if its class is `[0107]` (SAS controller) with
driver `mpt3sas`, the card has different firmware than ADR-0001 records.

Why this way: an earlier draft used `lspci -nnk | grep -iE 'sas|raid'`.
That also matched every "Rene**sas**" bridge on the board. Selecting by
class asks the precise question.

### Command 3 — read the state of the existing arrays

Purpose: do not build on a host whose existing arrays are unhealthy.

```
cat /proc/mdstat
```

`/proc/mdstat` is the md driver's live status (concept 4.10). `cat` prints
it. Read-only.

Expected:

```
Personalities : [raid1] [raid6] [raid5] [raid4]
md125 : active raid1 sdf3[0] sda3[1]
      615360 blocks super 1.0 [2/2] [UU]
      bitmap: 0/1 pages [0KB], 65536KB chunk

md126 : active raid1 sda2[1] sdf2[0]
      1047552 blocks super 1.2 [2/2] [UU]
      bitmap: 0/1 pages [0KB], 65536KB chunk

md127 : active raid5 sda1[1] sdc1[0] sdf1[3]
      1953257472 blocks super 1.2 level 5, 512k chunk, algorithm 2 [3/3] [UUU]
      bitmap: 0/8 pages [0KB], 65536KB chunk
```

How to read one entry:

| Piece | Meaning |
|---|---|
| `md127 : active raid5` | kernel name, state, level |
| `sda1[1] sdc1[0] sdf1[3]` | members and their slot numbers |
| `super 1.2` | metadata version (concept 4.5) |
| `512k chunk` | chunk size (concept 4.3) |
| `[3/3]` | 3 members expected, 3 working |
| `[UUU]` | one letter per slot: `U` up, `_` missing |
| `bitmap: 0/8 pages` | a write-intent bitmap exists; 0 pages dirty |

A progress bar line (`[==>.....] recovery = 12.3%`) appears under an array
that is rebuilding, resyncing or being checked.

If something is wrong: `[U_]` or `[UU_]` means degraded. Stop and fix that
first.

### Command 4 — confirm the three Seagate disks are blank

Purpose: `mdadm --create` will write to these disks. Prove they carry
nothing first.

```
for s in W9A63479 W9A7NB9T W9A9ZDXL; do
  d=/dev/disk/by-id/ata-ST1000DM010-2EP102_$s
  echo "== $d"
  sudo wipefs "$d"
  sudo mdadm --examine "$d"
done
```

| Token | Meaning |
|---|---|
| `for s in A B C; do ... done` | shell loop: run the body once per serial, with `$s` set to it |
| `d=/dev/...$s` | build the stable path for this disk and keep it in `$d` |
| `echo "== $d"` | print a heading so the output is readable |
| `sudo wipefs "$d"` | list filesystem, RAID and partition-table signatures on the device. With no options it only lists. (`-a` would erase them all; `-n` is a dry run for `-a`.) |
| `sudo mdadm --examine "$d"` | read the md superblock from this device, if any |
| `"$d"` in quotes | stops the shell splitting the value if it ever contained spaces; a good habit |

Changes: read-only.

Expected, three times:

```
== /dev/disk/by-id/ata-ST1000DM010-2EP102_W9A63479
mdadm: No md superblock detected on /dev/disk/by-id/ata-ST1000DM010-2EP102_W9A63479.
```

`wipefs` printing nothing means no signatures.

If it fails: `No such file or directory` means the by-id name is different
on your system. List what exists with
`ls /dev/disk/by-id/ | grep -v part`.

If a disk is not blank and you are certain it is the right disk:
`sudo wipefs -a <DISK_BY_ID_PATH>` erases the signatures. That is
destructive and has no undo.

### Command 5 — check whether TRIM reaches the SSDs

Purpose: decide whether to rely on discard anywhere in the design.

```
lsblk -D
```

| Column | Meaning |
|---|---|
| `DISC-GRAN` | smallest range that can be discarded |
| `DISC-MAX` | largest discard the device accepts in one request; `0B` means discard is not supported |

Result on this host: both 850 PRO disks and `md127` show `DISC-MAX 0B`.
Only the 870 EVO reports support (`128M`). An array can pass discards down
only if every member accepts them, so **TRIM does not reach the SSD tier**.
Recorded in ADR-0014. `fstrim` on anything in `ssd-vg` does nothing.

## 5.2 Build the HDD array

### Tool card: `mdadm`

| | |
|---|---|
| What it is | Creates, assembles, changes and monitors Linux software RAID (md) arrays. Package `mdadm`. |
| Talks to | the kernel md driver; superblocks on member devices; `/etc/mdadm.conf` |
| Use it when | Building an array, checking its health, replacing a failed disk, changing its settings |
| Related | `/proc/mdstat` (quick status), `/sys/block/mdN/md/` (live controls), `lsblk`, `smartctl` |
| Grammar | `mdadm MODE [array] [options] [member devices]` |
| Help | `man 8 mdadm`, `man 5 mdadm.conf`, `mdadm --create --help` |

Every `mdadm` command is one of these modes:

| Mode | Form | Does | Destructive? |
|---|---|---|---|
| Create | `mdadm --create /dev/md/NAME --level=L --raid-devices=N DISKS` | writes new superblocks, starts a new array | Yes, to the member disks |
| Detail | `mdadm --detail /dev/md/NAME` | full state of a running array | No |
| Examine | `mdadm --examine DISK` | reads the superblock on one member; works with the array stopped | No |
| Assemble | `mdadm --assemble --scan` | starts existing arrays from their superblocks | No |
| Manage | `mdadm /dev/md/NAME --fail DISK`, `--remove DISK`, `--add DISK` | mark failed, detach, attach a replacement | Changes the array |
| Grow | `mdadm --grow /dev/md/NAME ...` | change a live array: size, bitmap, consistency policy, member count | Changes the array |
| Monitor | `mdadm --monitor --scan` | watch arrays and report events; the `mdmonitor` service runs this | No |
| Misc | `--stop`, `--wait`, `--zero-superblock DISK` | stop an array, wait for a rebuild, erase a superblock | `--zero-superblock` is |

`--scan` means "all arrays" instead of one. `--detail` is for an array;
`--examine` is for a member disk. Mixing those two up is the most common
mistake.

Replacing a failed disk, for reference:

```
sudo mdadm /dev/md/hdd --fail <OLD_DISK_BY_ID> --remove <OLD_DISK_BY_ID>
# swap the physical disk, find the new one with: ls /dev/disk/by-id/ | grep -v part
sudo mdadm /dev/md/hdd --add <NEW_DISK_BY_ID>
```

### Command 7 — create the array

Purpose: combine the three Seagate disks into one RAID5 device with
write-hole protection (D1, D2).

```
sudo mdadm --create /dev/md/hdd --name=hdd --level=5 --raid-devices=3 \
  --chunk=512 --consistency-policy=ppl \
  /dev/disk/by-id/ata-ST1000DM010-2EP102_W9A63479 \
  /dev/disk/by-id/ata-ST1000DM010-2EP102_W9A7NB9T \
  /dev/disk/by-id/ata-ST1000DM010-2EP102_W9A9ZDXL
```

| Token | Meaning |
|---|---|
| `sudo` | needs root |
| `--create /dev/md/hdd` | Create mode; the device node to make |
| `--name=hdd` | name stored in the superblock (becomes `r730xd-01:hdd`) |
| `--level=5` | RAID5 |
| `--raid-devices=3` | number of active members |
| `--chunk=512` | chunk size in KiB |
| `--consistency-policy=ppl` | Partial Parity Log instead of a bitmap (concept 4.4) |
| `\` at line end | the command continues on the next line |
| three by-id paths | the members, whole disks, no partitions |

Changes: writes a superblock to each disk, creates `/dev/md/hdd`, starts a
background build. Anything previously on the disks is gone.

Expected:

```
mdadm: Defaulting to version 1.2 metadata
mdadm: array /dev/md/hdd started.
```

If it fails:

| Message | Cause | Fix |
|---|---|---|
| `must be super-user` | no `sudo` | add it |
| `cannot open /dev/disk/by-id/...: No such file or directory` | wrong path | copy the names from `ls /dev/disk/by-id/` |
| `You haven't given enough devices` | a typo split or dropped an argument; `-- chunk` with a space does this, because a bare `--` ends option parsing | retype the options carefully |
| `... appears to contain an existing filesystem` then a prompt | the disk is not blank | stop, go back to command 4 |

Verify:

```
sudo mdadm --detail /dev/md/hdd
```

```
        Raid Level : raid5
        Array Size : 1953258496 (1862.77 GiB 2000.14 GB)
      Raid Devices : 3
             State : clean, degraded, recovering
    Active Devices : 2
     Spare Devices : 1
        Chunk Size : 512K
Consistency Policy : ppl
    Rebuild Status : 1% complete
              Name : r730xd-01:hdd  (local to host r730xd-01)
              UUID : 33138201:5f40ed03:602fccaf:42e9527a
    Number   Major   Minor   RaidDevice State
       0       8       48        0      active sync   /dev/sdd
       1       8       64        1      active sync   /dev/sde
       3       8       16        2      spare rebuilding   /dev/sdb
```

`degraded, recovering` with one `spare rebuilding` is normal for a new
RAID5. `mdadm` starts it as two disks plus a spare and rebuilds onto the
spare, because that is faster than recalculating parity across three. The
array is usable while this runs but has no redundancy until it finishes.

Watch progress, or block until done:

```
cat /proc/mdstat
sudo mdadm --wait /dev/md/hdd
```

`--wait` returns when the rebuild completes. Expect roughly two hours for
1 TB disks. You may continue with 5.3 meanwhile; do not start the scrub in
5.7 until it has finished.

Undo (destroys the array):

```
sudo mdadm --stop /dev/md/hdd
sudo mdadm --zero-superblock <EACH_MEMBER_BY_ID>
```

Why this way: PPL over the default bitmap is D1. Whole disks instead of
partitions because these disks do nothing else.

### Command 8 — record every array in `/etc/mdadm.conf`

Purpose: pin each array's name to its UUID in the config file, so the
names are stable at every boot and `mdmonitor` has an explicit list to
watch.

Correction (2026-11-16): the first version of this step assumed the
installer had already written `ARRAY` lines for `boot_efi`, `boot` and
`pv00`. It had not; after the build the file held only the `hdd` line.
The boot arrays were still assembled at every boot, because the installer
put their UUIDs on the kernel command line as `rd.md.uuid=...` options
(check with `cat /proc/cmdline`) and udev assembles any array whose
stored host name matches this host. The config file should still list all
four: it is the one place that documents what should exist, and
`mdadm --assemble --scan` and the monitor read it.

```
sudo cp -a /etc/mdadm.conf /etc/mdadm.conf.pre-0.2
cat /etc/mdadm.conf
sudo mdadm --detail --scan | while read -r line; do
  uuid=${line##*UUID=}
  grep -q "$uuid" /etc/mdadm.conf || echo "$line" | sudo tee -a /etc/mdadm.conf
done
grep '^ARRAY' /etc/mdadm.conf
```

| Token | Meaning |
|---|---|
| `cp -a ... .pre-0.2` | keep a copy before editing |
| `cat /etc/mdadm.conf` | look at what is there first |
| `sudo mdadm --detail --scan` | print one `ARRAY` line per running array |
| `\| while read -r line; do ... done` | handle that output one line at a time; `-r` keeps backslashes literal |
| `uuid=${line##*UUID=}` | shell parameter expansion: delete the longest prefix of `$line` that ends in `UUID=`, leaving only the UUID |
| `grep -q "$uuid" /etc/mdadm.conf` | is that UUID already in the file? `-q` prints nothing; only the exit status matters |
| `\|\|` | run what follows only if the `grep` found nothing |
| `echo "$line" \| sudo tee -a /etc/mdadm.conf` | append the missing line as root |
| `grep '^ARRAY' /etc/mdadm.conf` | show the result |

Changes: appends the `ARRAY` lines that are missing; adds nothing that is
already present, so it is safe to run again.

Expected: `tee` echoes each line it adds; the last command lists four
lines:

```
ARRAY /dev/md/hdd metadata=1.2 name=r730xd-01:hdd UUID=33138201:5f40ed03:602fccaf:42e9527a
ARRAY /dev/md/boot_efi metadata=1.0 name=r730xd-01:boot_efi UUID=423d96c7:4ef8f42f:f3557aae:b2556f8b
ARRAY /dev/md/boot metadata=1.2 name=r730xd-01:boot UUID=0869e761:61d77346:802af477:b766ff67
ARRAY /dev/md/pv00 metadata=1.2 name=r730xd-01:pv00 UUID=cbd4af0f:a09c5e3b:eaac2317:a3411362
```

(Order and extra fields may differ.)

If it fails: the same UUID listed twice means an earlier `tee -a` was run
twice; delete the duplicate with `sudo vim /etc/mdadm.conf`.

Verify: `grep -c '^ARRAY' /etc/mdadm.conf` prints `4`.

Undo: `sudo cp -a /etc/mdadm.conf.pre-0.2 /etc/mdadm.conf`.

### Command 8a — bring the initramfs copy in line

The **initramfs** is the small temporary root filesystem the kernel loads
from `/boot` before the real root exists. It contains just enough tools
and configuration to assemble `pv00`, activate `ssd-vg` and mount root. It
may carry its own copy of `/etc/mdadm.conf`, made when it was built. A
copy that disagrees with the real file is a classic cause of arrays
assembling under the wrong name at boot.

#### Tool card: `dracut` and `lsinitrd`

| | |
|---|---|
| What they are | `dracut` builds initramfs images; `lsinitrd` lists and prints their contents. Package `dracut`. |
| Images | `/boot/initramfs-<KERNEL_VERSION>.img`, one per installed kernel, plus a rescue image |
| Use it when | After changing anything the boot stage needs: `/etc/mdadm.conf`, LVM or multipath config, storage drivers, encrypted-disk setup |
| Grammar | `dracut [options] [image] [kernel-version]`; `lsinitrd [options] [image]` |
| Safety | `lsinitrd` is read-only. `dracut -f` overwrites the boot image of the running kernel |
| Help | `man 8 dracut`, `man 1 lsinitrd`, `man 5 dracut.conf` |

| Option | Meaning |
|---|---|
| `dracut -f` | rebuild the image for the running kernel, overwriting it |
| `dracut -f --regenerate-all` | rebuild for every installed kernel |
| `lsinitrd` | list everything in the running kernel's image |
| `lsinitrd -f PATH` | print one file from inside the image (path without the leading `/`) |

```
lsinitrd -f etc/mdadm.conf
```

Read-only. If it prints nothing, the image has no copy and nothing more is
needed. If it prints a file that differs from `/etc/mdadm.conf`, rebuild:

```
sudo cp -a /boot/initramfs-$(uname -r).img /boot/initramfs-$(uname -r).img.pre-mdadm
sudo dracut -f
lsinitrd -f etc/mdadm.conf
```

| Token | Meaning |
|---|---|
| `$(uname -r)` | the running kernel's version string, substituted into the path |
| `cp -a ... .pre-mdadm` | keep the working image; `/boot` has room for one extra copy |
| `dracut -f` | rebuild the image for the running kernel |
| `lsinitrd -f etc/mdadm.conf` | confirm the new image carries all four lines |

Expected: `dracut` prints little or nothing and takes under a minute; the
final command shows the four `ARRAY` lines.

If the host then fails to boot: choose the "rescue" entry in the GRUB
menu, which has its own image, and restore the copy:
`sudo cp -a /boot/initramfs-$(uname -r).img.pre-mdadm /boot/initramfs-$(uname -r).img`.

Verify: reboot during the next convenient window and run
`cat /proc/mdstat` and `ls -l /dev/md/`.

## 5.3 Volume group, logical volumes, filesystems, mounts

### Tool card: LVM (`pv*`, `vg*`, `lv*`)

| | |
|---|---|
| What it is | The Logical Volume Manager. One package, `lvm2`; many commands named by layer. |
| Talks to | the kernel device-mapper; metadata stored on each PV; `/etc/lvm/lvm.conf` |
| Use it when | Creating, growing, snapshotting or removing volumes |
| Grammar | `<layer><verb> [options] TARGET`, e.g. `lvcreate`, `vgs`, `pvdisplay` |
| Help | `man 8 lvm`, `man 7 lvmthin`, `lvcreate --help` |

| Layer | Create | Summary (one line each) | Detail | Grow | Remove |
|---|---|---|---|---|---|
| Physical volume | `pvcreate DEV` | `pvs` | `pvdisplay` | `pvresize` | `pvremove` |
| Volume group | `vgcreate VG PV` | `vgs` | `vgdisplay` | `vgextend VG PV` | `vgremove` |
| Logical volume | `lvcreate ...` | `lvs` | `lvdisplay` | `lvextend` | `lvremove` |

`lvcreate` options you will use:

| Option | Meaning |
|---|---|
| `-L 300G` | size in binary units (GiB) |
| `-l 90%FREE` | size as a share of the VG's free space (also `100%FREE`, or a number of extents) |
| `-n NAME` | name of the new LV |
| `--type thin-pool` | make a thin pool |
| `--type thin --thinpool POOL -V 40G` | make a thin LV of virtual size 40 GiB in POOL |
| `-s -n SNAP VG/LV` | snapshot (add `-L SIZE` if the origin is thick) |

`lvs` is the command you will run most. Useful forms:

```
sudo lvs                                  # all LVs
sudo lvs -a                               # include hidden parts of thin pools
sudo lvs -o lv_name,lv_size,data_percent,metadata_percent ssd-vg
```

The create, summary and detail commands need root. Read-only: `pvs`, `vgs`,
`lvs`, `*display`. Destructive: `*remove`, and `lvreduce`.

### Command 9 — make the array a physical volume and create the group

```
sudo pvcreate /dev/md/hdd
sudo vgcreate hdd-vg /dev/md/hdd
```

| Token | Meaning |
|---|---|
| `pvcreate /dev/md/hdd` | write an LVM label to the array so LVM can use it |
| `vgcreate hdd-vg /dev/md/hdd` | create a volume group named `hdd-vg` containing that PV |

Changes: LVM metadata written to the start of the array.

Expected:

```
  Physical volume "/dev/md/hdd" successfully created.
  Volume group "hdd-vg" successfully created
```

If it fails: a long block ending `Failure to communicate with kernel
device-mapper driver` means you ran it without `sudo`.

Verify: `sudo vgs hdd-vg` shows `VSize <1.82t`.

Undo: `sudo vgremove hdd-vg` then `sudo pvremove /dev/md/hdd`.

### Command 10 — create the three logical volumes

Purpose: separate volumes so one filling up cannot starve the others.

```
sudo lvcreate -L 1T   -n backups hdd-vg
sudo lvcreate -L 300G -n bulk    hdd-vg
sudo lvcreate -L 150G -n isos    hdd-vg
```

| Token | Meaning |
|---|---|
| `-L 1T` | 1 TiB |
| `-n backups` | LV name |
| `hdd-vg` | the group to take the space from |

Changes: three block devices appear, `/dev/hdd-vg/{backups,bulk,isos}`.

Expected: `Logical volume "backups" created.` and likewise for the others.

If it fails: `Volume group "hdd-vg" has insufficient free space` means the
sizes add up to more than the group.

Verify:

```
sudo vgs hdd-vg
```

```
  VG     #PV #LV #SN Attr   VSize  VFree
  hdd-vg   1   3   0 wz--n- <1.82t <388.77g
```

Three LVs, about 388 GiB left free on purpose for later volumes (packet
captures in Phase 6) or for growing these.

Undo: `sudo lvremove hdd-vg/<NAME>` (destroys that volume's contents).

Growing one later is one command, online:
`sudo lvextend -r -L +100G hdd-vg/bulk` (`-r` grows the filesystem too).

### Command 11 — create the filesystems

```
for lv in backups bulk isos; do sudo mkfs.xfs /dev/hdd-vg/$lv; done
```

| Token | Meaning |
|---|---|
| `for lv in ...; do ...; done` | run once per volume name |
| `mkfs.xfs DEVICE` | write a new, empty XFS filesystem to the device. Package `xfsprogs`. |

Changes: each volume is formatted. Anything on it is gone.

Expected, per volume, a block of parameters. The two worth reading:

```
data     =                       bsize=4096   blocks=78641152, imaxpct=25
         =                       sunit=128    swidth=256 blks
```

`bsize=4096` is the block size. `sunit=128` blocks × 4 KiB = 512 KiB, the
RAID chunk. `swidth=256` blocks = 1 MiB = two data chunks per stripe.
`mkfs.xfs` read the array's geometry and aligned itself to it without being
told.

If it fails: `mkfs.xfs: /dev/hdd-vg/x appears to contain an existing
filesystem` means it is refusing to overwrite. Check you have the right
device; `-f` forces it.

Verify: `lsblk -f /dev/md/hdd` shows `xfs` and a UUID for each volume.

Undo: none. Reformat or remove the LV.

Why XFS: it is the RHEL default, it grows online, and it is what the
RHCSA/RHCE material uses. XFS cannot be shrunk.

### Command 12 — add the mounts to `/etc/fstab`

Purpose: mount the three filesystems now and at every boot, identified by
UUID.

```
sudo mkdir -p /srv/backups /srv/bulk /var/lib/libvirt/isos
sudo blkid /dev/hdd-vg/backups /dev/hdd-vg/bulk /dev/hdd-vg/isos
sudo cp -a /etc/fstab /etc/fstab.pre-0.2
sudo vim /etc/fstab
```

| Token | Meaning |
|---|---|
| `mkdir -p A B C` | create the mount-point directories; `-p` creates missing parents and does not complain if they exist |
| `blkid DEV DEV DEV` | print each volume's UUID |
| `cp -a SRC DST` | keep a copy of the file before editing; `-a` preserves owner, mode and timestamps |
| `vim /etc/fstab` | edit as root |

Add these three lines (the UUIDs are this host's):

```
UUID=3a8fc48c-24bb-4b62-936e-f25c0f1a5d73 /srv/backups           xfs defaults 0 0
UUID=723273be-691e-430f-a5dd-d11c5242eb9d /srv/bulk              xfs defaults 0 0
UUID=be3e0043-beea-47b0-8876-e708f9b45ee9 /var/lib/libvirt/isos  xfs defaults 0 0
```

Fields: what to mount, where, filesystem type, mount options, dump flag
(unused), fsck order (0 = never; XFS does not use it).

Then check the file and mount:

```
sudo findmnt --verify
sudo systemctl daemon-reload
sudo mount -a
```

| Token | Meaning |
|---|---|
| `findmnt --verify` | parse `/etc/fstab` and report mistakes before they can break a boot |
| `systemctl daemon-reload` | systemd builds mount units from `/etc/fstab`; this makes it re-read the file |
| `mount -a` | mount everything in `/etc/fstab` that is not already mounted |

Changes: `/etc/fstab` edited; three filesystems mounted.

If it fails:

| Message | Cause |
|---|---|
| `mount: ... must be superuser to use mount` | `sudo` missing on `mount -a` (in `a && b`, `sudo` covers only `a`) |
| `can't find UUID=...` | a typo in the UUID |
| `mount point does not exist` | the directory was not created |

Verify:

```
df -hT /srv/backups /srv/bulk /var/lib/libvirt/isos
```

```
Filesystem                  Type  Size  Used Avail Use% Mounted on
/dev/mapper/hdd--vg-backups xfs   1.0T  ...             /srv/backups
/dev/mapper/hdd--vg-bulk    xfs   300G  ...             /srv/bulk
/dev/mapper/hdd--vg-isos    xfs   150G  ...             /var/lib/libvirt/isos
```

Each path must show an `hdd--vg-*` device, not `ssd--vg-root`.

`findmnt` answers the same question for one path at a time:
`findmnt /srv/bulk`. It takes a single target; given three it prints
nothing, which is what happened during the build.

Undo: `sudo umount <MOUNT_POINT>`, remove the line, or restore
`/etc/fstab.pre-0.2`.

Recommended change (not applied on the build day): replace `defaults` with
`defaults,nofail` on these three lines. With `defaults`, a failed HDD array
stops the boot, even though root and the VMs do not need that array.
systemd then tries to open an emergency shell, and on this host root is
locked, so the console prints `Cannot open access to console, the root
account is locked` and the only way in is rescue media. With `nofail` the
host boots and the three paths are empty until the array is fixed. The
cost is that a missing mount is silent until something monitors it; the
runbook health check and, later, a Module 1.5 alert cover that.

### Tool card: `mount`, `umount`, `findmnt`, `df`

| Command | What it is | Typical use |

| | |
|---|---|
| What it is | The RHEL package manager: installs, updates and removes RPM packages and resolves their dependencies. |

### Command 15 — write the repository definition

```
sudo tee /etc/yum.repos.d/rhel-dvd.repo >/dev/null <<'EOF'
[dvd-baseos]
name=RHEL9.5 DVD BaseOS
baseurl=file:///srv/bulk/repo/rhel9.5/BaseOS
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release

[dvd-appstream]
name=RHEL9.5 DVD AppStream
baseurl=file:///srv/bulk/repo/rhel9.5/AppStream
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release
EOF
```

| Token | Meaning |
|---|---|
| `sudo tee FILE` | write standard input to FILE as root |
| `>/dev/null` | discard `tee`'s copy to the screen |
| `<<'EOF'` ... `EOF` | a here-document: everything up to the line `EOF` becomes standard input. The quotes around `EOF` stop the shell expanding `$` or backticks inside |
| `[dvd-baseos]` | repository ID, used with `--repo=` |
| `name=` | human-readable name |
| `baseurl=file:///srv/...` | where the repository is. `file://` is the scheme; the third `/` starts the absolute path |
| `enabled=1` | use this repository |
| `gpgcheck=1` | verify package signatures |
| `gpgkey=` | the public key to verify with; this file is installed with the OS |

Changes: creates or overwrites `/etc/yum.repos.d/rhel-dvd.repo`.

Verify:

```
sudo dnf clean all
sudo dnf repolist -v | grep -E 'Repo-id|Repo-pkgs'
```

Expected: both repository IDs, each with a package count in the thousands.

Messages you can ignore on this host: `This system is not registered with
an entitlement server` and `Unable to read consumer identity`. They come
from the subscription plugin and are true: the host is offline.

If it fails:

| Message | Cause |
|---|---|
| `Cannot download repomd.xml: Empty mirrorlist and no basepath specified` | `baseurl` is malformed, for example `file///` with the colon missing |
| `Curl error (37): Couldn't read a file:// file ... repomd.xml` | the path in `baseurl` is wrong, or `/srv/bulk` is not mounted |
| `Permission denied` writing the file | you used `sudo cat > FILE`; the redirect ran as you (concept 4.15) |

Undo: `sudo rm /etc/yum.repos.d/rhel-dvd.repo`.

Why this way: a here-document through `tee` writes the whole file in one
step and can be re-run. Editing a `baseurl` in place with `sed` is where
the build day's typos came from.

Dependency created: `dnf` now needs `/srv/bulk` mounted.
