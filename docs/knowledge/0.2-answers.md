## B. Concept questions

1. A stripe update writes data and parity as two separate writes. **Must:**
   power is lost between them, leaving them inconsistent; nothing notices;
   **later a member fails** and the stripe is reconstructed from the wrong
   parity, returning corrupt data silently. Both events are required.
2. It records which regions were being written so that after a crash only
   those are resynced. It makes recovery faster. It does not record what
   the correct parity was, so if a disk is missing the stripe still cannot
   be reconstructed correctly.
3. Both use the same area of the array's metadata, and the kernel does
   not support them together. Choosing PPL costs write performance and
   gives up the bitmap's fast partial resync (which PPL makes unnecessary
   after a crash).
4. If the pool fills, every thin volume in it stalls. Root is outside it,
   so the host keeps running and can be used to fix the problem.
5. A snapshot of a thick volume needs its own space in the volume group.
   That space is for snapshotting `root` before risky changes.
6. Data space at 100% and metadata space at 100%. In both cases writes to
   every thin volume in the pool block or fail, so all VMs freeze. **Must**
   mention metadata as the second way.
7. They have no error-recovery control and may retry a bad sector for
   longer than the kernel's command timeout (90 s with `megaraid_sas`).
   The kernel then resets the disk, md sees an I/O error and ejects a
   member that was only slow. During a rebuild that loses the array.
   180 s lets the disk finish.
8. `system` is the host-wide hypervisor run as root; `session` is a
   private per-user instance. `virsh` as an unprivileged user defaults to
   `session`. The `isos` pool was first defined there and was invisible
   to the system instance.
9. The files would have been written to the root filesystem under
   `/srv/bulk`, then hidden when `hdd-vg/bulk` was mounted over that
   directory. Root would carry 12 GB of invisible data and the repository
   would appear empty.
10. Version 1.0 keeps the superblock at the end of the partition, so the
    start of the partition looks like a plain FAT filesystem. The firmware
    reads the EFI partition directly and knows nothing about md.

## C. Read this command

1. `echo check` prints the word `check`; `|` pipes it; `sudo tee FILE`
   runs `tee` as root, which writes its input to the file (and to the
   screen). The file is the md control file for array md124. Writing
   `check` starts a scrub. **Must** explain why not `sudo echo check >`:
   the redirect is done by the unprivileged shell.
2. Create a logical volume of type thin, drawing from pool `vmpool`,
   with virtual size (`-V`) 40 GiB, named `vm-a`, in group `ssd-vg`.
   Prints `Logical volume "vm-a" created.` Creates `/dev/ssd-vg/vm-a`.
   Uses almost no real space until written.
3. `mdadm --detail --scan` prints an `ARRAY` line for every running array;
   `grep hdd` keeps the one for `hdd`; `sudo tee -a` appends it to
   `/etc/mdadm.conf` as root and shows it. **Must** note `-a` appends and
   that running it twice adds a duplicate line. Credit also for noting
   that the installer had written no lines for the other arrays, so this
   left the file with one line, not four.
4. A udev rule. Match (`==`): the event is add or change; a block device;
   kernel name `sda`-`sdz` (whole disks); a parent device's `model`
   attribute starts with `ST1000DM010`. Assign (`=`): write `180` to this
   device's `device/timeout` file in `/sys`. **Must** distinguish `==`
   from `=` and `ATTRS` (device or parents) from `ATTR` (this device).
5. As root, show the self-test log (`-l selftest`) of the disk addressed
   by its stable by-id path, talking to it as a SATA disk behind a SCSI
   layer (`-d sat`). Prints a table of past self-tests with status and
   power-on hours. Changes nothing.

## D. Pick the tool

1. `lspci -nnk`, looking at the Ethernet controller entries and their
   "Kernel driver in use" line. (`-d ::0200` narrows to network
   controllers.) Credit also for following with `ip link`.
2. `lsblk -d -o NAME,SERIAL,MODEL` to find its current device, or go
   straight to `/dev/disk/by-id/`; then `sudo mdadm --examine` on it or
   its partitions, or read `lsblk` for the md devices beneath it.
   **Must** use `--examine` (member), not `--detail` (array), or use
   `lsblk`.
3. `sudo blkid /dev/<vg>/<lv>` (or `lsblk -f`) for the filesystem UUID;
   the field is `UUID=<value>`.
4. `systemctl is-enabled UNIT` and `systemctl is-active UNIT` (or
   `systemctl status UNIT`); the reason is in `journalctl -u UNIT -b`.
5. `udevadm info -a -n /dev/<disk>` lists matchable attributes for the
   device and its parents; `sudo udevadm test /sys/block/<disk>` shows
   what the rules do and reports syntax errors.

## E. Decide

1. D1 / ADR-0011. With clean shutdowns guaranteed, the write hole's
   trigger is removed, so a bitmap is acceptable. `pv00` keeps its bitmap
   deliberately instead of being converted; `hdd` may be switched from
   PPL back to a bitmap. Gain: write performance. Lose: protection in the
   case where the UPS itself fails or the host crashes for another reason.
   **Must** name both arrays and say the bitmap alone still does not
   close the hole.
2. Set a short disk-side recovery limit (`smartctl -l scterc,70,70`,
   applied at boot) and remove or relax the 180 s udev rule. Keep the
   weekly scrub, SMART monitoring and the alert hook. Update the model
   match in the rule and the `smartd.conf` lines for the new by-id names.
   Write an ADR superseding 0013.

## F. Failure scenarios

1. This is the write-hole sequence on the array that has no PPL. Stripes
   that were mid-write at the power cut may have bad parity, and a member
   is now returning errors. Blast radius: root and every VM disk. First:
   do not remove or fail the disk while the resync runs; let the resync
   finish if it can, check SMART on the suspect disk, and get backups of
   anything important before any disk replacement. Then treat VM
   filesystems as suspect. **Fail** the answer if it removes a member
   during resync.
2. The pool's data space is exhausted. All thin volumes block. Root is
   thick, so the host is unaffected. First: free space in the pool by
   removing snapshots and unused thin volumes (`sudo lvs ssd-vg` to find
   them). Extending the pool into the 180 GiB reserve is possible
   (`lvextend`) but spends the root-snapshot space; say so if you choose
   it. **Fail** the answer if it deletes a VM disk without checking what
   it is.
3. The `hdd` array has lost its third member and is degraded: no
   redundancy, still serving data. Blast radius: backups, repo, ISOs at
   risk if a second disk fails. First: `sudo mdadm --detail /dev/md/hdd`
   and the kernel log to see which disk and why; SMART on it; if it was
   ejected but is healthy and visible, re-add it; if dead, replace per
   the runbook. Avoid heavy I/O until rebuilt. **Fail** the answer if it
   recreates the array.
4. A filesystem in `/etc/fstab` could not be mounted, most likely because
   `hdd` did not assemble; systemd wants an emergency shell and root has
   no password. The OS and data are intact. First: boot rescue media,
   mount the installed system, comment out or add `nofail` to the three
   `hdd-vg` lines, reboot, then investigate the array from the running
   host.
5. `dnf` cannot read the repository index. Most likely `/srv/bulk` is not
   mounted. First: `findmnt /srv/bulk`; if empty, `cat /proc/mdstat` and
   `sudo vgs` to see whether the array and group are present, then
   `sudo mount -a`. If it is mounted, check the `baseurl` path in
   `/etc/yum.repos.d/rhel-dvd.repo`.
