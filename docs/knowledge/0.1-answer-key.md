# Answer key — Module 0.1

**Open only after writing your answers to `0.1-check.md`.**

## Pass bar

- Teach-back: at least 8 of the 10 required elements below.
- Concept questions: at least 10 of 12 fully correct. A partial answer that misses
  the "why" counts as wrong.
- Failure scenarios: all 5 must name a safe first action and the most likely cause.
  Any scenario whose first action could destroy data or lock you out is a fail of
  the whole check.

## Part 1: Teach-back — required elements

1. Isolated direct link (bridged VM NIC, static, no gateway) so nothing touches the
   home LAN; the iDRAC on a dedicated port, static IP.
2. First access with password-only SSH and `getsysinfo` to prove path, crypto and
   firmware in one step.
3. Before-state capture to files before any change: evidence and diff baseline.
4. Firmware compared per component against Dell for the service tag; update only
   with matching packages; freeze.
5. Named admin created (username and password first), privilege verified
   `0x1ff`, key installed, key login proven, **then** root scrambled and disabled,
   tested after closing reused connections.
6. Services: SSH and HTTPS (TLS 1.2) and the encrypted Virtual Console on;
   IPMI, VNC, Telnet, SNMP off; IP blocking; NTP by IP.
7. BIOS: UEFI, VT, OS power profile, AC recovery Last, `SerialComm=OnConRedirCom2`
   **and** `SerialPortAddress=Serial1Com1Serial2Com2`, one job; serial path proven
   at POST; Secure Boot as a separate job; kernel `console=ttyS1,115200n8`.
8. Bay mapping by serial and by pulling drives while empty, because locate LEDs
   don't work in HBA mode.
9. Memory read only after POST completes; missing DIMMs isolated by swap test;
   thorough memory test before trusting the host.
10. Redundancy policy Input Power Redundant; export over a temporary NFS share,
    wait for the job, validate XML, check secrets are masked, close the share.

## Part 2: Concept answers

1. HBA mode passes real disks to mdadm. RAID0-per-disk puts controller metadata on
   every disk, hides SMART behind the controller, ties disk replacement to
   controller reconfiguration, and stacks two RAID layers. Also arrays wouldn't
   import cleanly on a non-PERC HBA. (Any two.)
2. BIOS `set` only stages a pending value. A Lifecycle Controller job
   (`jobqueue create BIOS.Setup.1-1`) applies it during a reboot. Only one BIOS
   configuration job can be pending, so stage everything first and create one job.
3. `SerialComm` chooses which COM port the console is redirected to.
   `SerialPortAddress` chooses which device is on that port (serial device 1 =
   rear connector, serial device 2 = iDRAC). With `Serial1Com2Serial2Com1`, COM2 was
   the physical connector, so all output went there and the iDRAC never saw it.
4. Internal DNS and FreeIPA will run on the host the iDRAC manages. The iDRAC is
   needed most when the host is down; anything it depends on must not live on the
   host. Local accounts work with every VM down.
5. IPMI 2.0's RAKP exchange hands an unauthenticated client a salted password hash
   that can be cracked offline. UDP 623 also carries RMCP presence pings, which the
   iDRAC answers regardless, so nmap marks it open. Proof: `ipmi-version` script
   returns nothing and `ipmitool -I lanplus` cannot establish a session.
6. `open`: a service answered. `closed`: the host replied that nothing listens
   (TCP reset or ICMP port unreachable). `filtered`: no reply (usually a firewall).
   `open|filtered`: UDP silence, which could be either. UDP has no handshake, so
   silence is ambiguous and a reply may come from a transport-level responder
   rather than the service.
7. Two bad sticks, or a fault in CPU1 channel 3 (seating, socket pins, memory
   controller). Swap A4↔B4 and A8↔B8. If the missing pair moves to B4/B8, the
   sticks are bad (what happened). If A4/A8 stay missing with known-good sticks in
   them, the channel is at fault.
8. RAID5 protects against a disk returning no data, not against wrong data. Memory
   corruption gets written to disk with freshly computed, valid parity, so RAID
   cannot detect or repair it. A failed disk is detected and rebuilt from parity.
9. `-r pwrcycle` cuts power instantly, like pulling the plug, which can corrupt
   filesystems and leave RAID parity inconsistent. Create the job without `-r` and
   reboot cleanly from the OS (`systemctl reboot`), which triggers the job.
10. Scrambling: if root is ever re-enabled (by mistake or by an attacker with
    access), it doesn't come back with a known password. `ssh -O exit`: an open
    `ControlMaster` connection would let the "root denied" test succeed falsely by
    reusing an already-authenticated session.
11. Metadata 1.0 sits at the end of each partition, so firmware sees each member as
    a plain FAT filesystem and can boot from it. Two entries, one per ESP copy, so
    the firmware can boot from the surviving disk if one fails.
12. The iDRAC treats the PSUs as a redundant pair, checks either can carry the load
    alone, and raises an alert if redundancy is lost. It does not protect against
    losing the circuit both PSUs share, or a utility outage; only a UPS does that.

## Part 3: Scenarios

**A.** Causes: the iDRAC has hung, or the VM's path (Fusion bridge, wrong NIC) is
broken. First safe action: test from the middle of the path — ping from the Mac on
the same cable (192.168.0.99/24). Mac works → stale Fusion bridge: disconnect and
reconnect the adapter, flush ARP, re-up `idrac-link`. Mac fails too → iDRAC hung:
`racadm racreset` if any channel works, otherwise shut the host down cleanly and AC
power-cycle both PSUs. Fail if the answer starts by power-cycling a running host.

**B.** Press Enter first (the prompt only prints once). Then check
`BIOS.SerialCommSettings` (`SerialComm`, `SerialPortAddress`, `RedirAfterBoot`),
`iDRAC.SerialRedirection.Enable`, then on the host `/proc/cmdline` for
`console=ttyS1,115200n8` and `serial-getty@ttyS1`. Most likely after a BIOS reset:
`SerialPortAddress` reverted. A BIOS fix with the OS running is a job without `-r`
plus a clean reboot.

**C.** Do **not** pull anything yet; locate LEDs don't work in HBA mode. Get the
failed member's serial (`lsblk -o NAME,MODEL,SERIAL`, `mdadm --detail`, or
`racadm storage get pdisks -o`), match it to the bay map and the caddy label, then
mark it failed and remove it from the arrays in mdadm before pulling. Cause:
marginal connection or failing drive (this is the known suspect, S3D2NX0J603337T).
Fail if the answer pulls a caddy by guess or by `sdX` name.

**D.** Nothing is wrong: the reads ran during POST, so the iDRAC returned stale
cached inventory and the controller hadn't initialized yet. First action: wait for
POST to finish (login prompt on `console com2`), then re-read. Only if the second
read still disagrees with the installed count (12 on this host, ADR-0010) is it
real.

**E.** That every secret is masked. Run
`grep -iE 'password|community|secret' <file> | grep -v '\*\*\*\*\*\*'` and judge
each line; expected leftovers are community names (`public`, services off), a
policy flag, empty iSCSI CHAP fields and `PasswordStatus`. Also confirm it's the
current export (job `Completed` before copying; a known recent change such as
`SNMP.1#AgentEnable=Disabled` is present), and validate with `xmllint --noout`.
